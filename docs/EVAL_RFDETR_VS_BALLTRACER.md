# 对比评测 · RF-DETR-SoccerNet（转播级 SOTA） vs BallTracer（业余域自研）

> 版本 v0.1（2026-10-19）。同一批视频、同一份真值、同一把尺子。
> 结论先行：**官方"业余足球不在适用范围内"的声明基本成立——但不是"完全失效"，而是"置信度标定崩坏"**。
> 无阈值召回 RF-DETR 84.0% 反而高于 BallTracer 76.2%，但同阈值下球候选精度仅 **7.6%**（BallTracer 60.0%），
> 每帧 11.9 个球误检，输出**不能直接使用**。

---

## 1. 被测对象

| | RF-DETR-SoccerNet | BallTracer（自研） |
|---|---|---|
| 来源 | HuggingFace `julianzu9612/RFDETR-Soccernet` | 本仓库 `balltracer` 包（tag v1.0.0） |
| 骨干 | DINOv2-**base**(768) + windowed attention(num_windows=4) | YOLO11n 领域微调 |
| 训练域 | SoccerNet-Tracking，**4.2 万张转播画面** | 本夜场片段自标 |
| 类别 | ball / player / referee / goalkeeper（4 类） | ball（单类）+ person |
| 输入 | 560×560（resolution=560, patch=14） | 2× 上采样 + SAHI 3 瓦片，imgsz 1280 |
| 官方标称 | mAP@50 = **85.7%**（转播域） | 裸检测 70.2% / 完整管线 77.3%（见 §4） |
| 权重 | `checkpoint_best_regular.pth`（1566MB） | `runs/ball_tile_v3/weights/best.pt` 等 3 个 |

**权重架构考古（复现必读）**：仓库 `config.json` 标注 "RF-DETR-Large / 128M" 是**错标**，
仓库自带 `inference.py` 用 `RFDETRBase()` + `strict=True` 加载，在现行 rfdetr 版本上**必然失败**。
真实架构只能从 checkpoint 内嵌的训练 `args` 还原：

```
encoder=dinov2_windowed_base   hidden_dim=384   sa_nheads=12   ca_nheads=24
dec_layers=3  num_queries=300  group_detr=13   two_stage=True
projector_scale=['P3','P5']    dec_n_points=4  resolution=560  positional_encoding_size=37
```

按此重建后 `load_state_dict` 得到 **missing=0 / unexpected=0**（精确匹配）。
依赖链：`rfdetr==1.2.1` + `transformers==4.51.3`（5.x 移除了 `_init_backbone` /
`find_pruneable_heads_and_indices` / `get_aligned_output_features_output_indices`，与 rfdetr 1.2.1 不兼容）。

## 2. 评测域与真值（两侧完全一致）

- 视频：`full.mp4`，**854×356**（非标 2.4:1）、29.97fps、**夜场低清固定机位**；
- 真值：`dets_track/{0..7}.json` 人工锚点，`ball` 非空且 `real=True`，每 3 帧 1 个，共 **181 个可见球锚点**；
- 球在画面中的典型大小 ≈ **0.008 归一化 ≈ 7 像素**（GT 球框本身极小）；
- 帧索引：`fi = int(segs[si][0] * fps) + a * 3`，两侧用同一公式取帧。

## 3. 单帧口径：召回-阈值曲线（conf=0.05 推理，R=0.02，181 锚点）

先以 permissive 阈值跑一遍，再按阈值统计，得到完整曲线：

| conf 阈值 | RF-DETR | BallTracer（3 模型融合） |
|---|---|---|
| ≥0.05 | 73.5% | **76.2%** |
| ≥0.10 | 66.3% | **75.1%** |
| ≥0.20 | 61.9% | **66.9%** |
| ≥0.30 | 53.6% | 44.8% |
| ≥0.40 | 48.1% | 36.5% |
| ≥0.50 | 37.6% | 25.4% |
| **无阈值** | **84.0%** | 76.2% |

读法：

- **中低阈值段 BallTracer 领先**（0.05/0.10/0.20 三段各高 2.7~8.8 个点）——业余域专用模型在可用阈值区间仍占优；
- **高阈值段 RF-DETR 反超**（≥0.30 起）——BallTracer 的 conf 在 0.3 以上快速衰减，RF-DETR 到 0.5 还有 37.6%；
- **无阈值 84.0% vs 76.2%** 说明 RF-DETR 的特征提取能力并未失效，"球在特征空间的哪里"它知道，只是**置信度标定在业余域完全失真**。

## 4. 精度侧：这才是分水岭（conf=0.05, R=0.02, 181 锚点）

召回数字会掩盖代价。两侧同口径统计球类别候选：

| 指标 | RF-DETR | BallTracer |
|---|---|---|
| 平均每帧球候选数 | **12.83** | **1.27** |
| 平均每帧球误检（FP） | **11.85** | **0.51** |
| 球候选总数 / TP / FP | 2322 / 177 / 2145 | 230 / 138 / 92 |
| **球候选精度** | **7.6%** | **60.0%** |
| 命中框 conf 中位数 | 0.365 | 0.375 |
| 观测到的最大球 conf | 0.734 | 0.738 |

**RF-DETR 每帧吐 12.8 个球候选、其中 11.9 个是误检**——精度 7.6%，即 13 个候选里只有 1 个是真的。
注意两侧命中框的 conf 中位数几乎相同（0.365 vs 0.375）、最大 conf 也几乎相同（0.734 vs 0.738）：
**RF-DETR 不是"没有高置信度的正确检出"，而是"同样置信度下混着大量错误检出"**——
它的 conf 在业余域丧失了区分能力，转播域 85.7% mAP 所依赖的置信度分布整体失效。

另外 RF-DETR 在 100% 的帧上都输出了全部 4 个类别（ball/player/referee/goalkeeper）——
业余夜场并没有"门将"，referee 每帧必现同样是过度触发的证据。

## 5. 时序融合口径（R=0.03, 邻帧 r=1, conf=0.05, NMS 0.02, 邻帧 0.6 衰减）

给两侧各自套上"邻帧补检 + NMS 合并"（BallTracer 侧为其完整 3 模型管线，RF-DETR 侧为单模型）：

| | 召回 |
|---|---|
| RF-DETR + 时序 | **81.2%（147/181）** |
| BallTracer + 时序 | 77.3%（140/181） |

RF-DETR 靠"多吐候选 + 邻帧补"反超 3.9 个点——这正是 §4 那个 7.6% 精度的另一面：
候选足够多时，真球总有一帧能被邻帧捞回来。**代价是每帧 12.8 个球候选的后续筛选负担**
（BallTracer 的物理速度门限 + Viterbi 长时轴清理本质上就是为消化这种候选洪水设计的）。

## 6. 速度

| | 推理速度（RTX GPU） | 每帧前向次数 |
|---|---|---|
| RF-DETR | **30.1 FPS** | 1 次（854×356 → 560×560） |
| BallTracer | —（未单独测，受 SAHI 主导） | 3 模型 × (1 全图 + 3 瓦片) ≈ 16 次，imgsz 1280 |

RF-DETR 单帧前向快一个量级，这是 DINOv2 + 单次前向架构的天然优势；
但要在本域达到同等召回必须把阈值压到 0.05 以下，且必须外挂候选筛选层。

## 8. 结论

1. **官方声明成立，但机制比声明更微妙**。不是"检测不到球"——无阈值召回 84.0% 甚至高于 BallTracer；
   而是**置信度标定在业余低清域整体失效**：转播域 85.7% mAP 依赖的 conf 分布，在 854×356 夜场、
   7px 球面上退化为"真候选 conf 0.365、假候选 conf 0.06 却大量并存"的无区分状态。
2. **同阈值单帧召回，BallTracer 仍略胜**（76.2% vs 73.5% @0.05；75.1% vs 66.3% @0.10），
   且**每帧球候选少 10 倍、精度高 8 倍**（60.0% vs 7.6%）。业余域专用微调 + 物理门限的路线在本域依然最优。
3. **RF-DETR 的价值在"候选生成器"而非"检测器"**：81.2%（时序）的反超说明它适合作为
   高召回候选源，但必须外挂一层筛选（BallTracer 已有的物理门限 + Viterbi 正是此层）。
4. **社区权重的工程陷阱**：config.json 错标 Large、自带 inference.py 严格加载必败、
   依赖 rfdetr 1.2.1 + transformers 4.x 的组合。复现请以 checkpoint 内 `args` 为准（见 §1）。
5. **给选型的直接建议**：本域继续用 BallTracer 做主链；若未来要扩人物/裁判/门将语义，
   可把 RF-DETR 的 4 类候选作为第二来源接入，但球链路不要替换。

## 10. 追加口径：仅保留 conf≥0.40 的球、去掉人的标签（v0.2，用户要求）

按"只要 0.40 以上的球、人的标签去掉"重出 5 段视频（`rf_out40/`，脚本新增
`--ball-thr 0.40`，人类别不再绘制；轨迹与统计同样只认 0.40 以上的球）。
推理仍在 0.05 全量跑，只在显示/统计层过滤，因此下面的数字与 §3~§5 完全同源。

### 10.1 逐段球覆盖率（每帧最佳球 conf ≥ 0.40 的帧占比）

| 片段 | 帧数 | @0.10 | @0.30 | **@0.40** | @0.50 | 最大 conf | ≥0.40 时平均 conf |
|---|---|---|---|---|---|---|---|
| seg0 M c | 450 | 25.3% | 25.3% | **25.3%** | 15.1% | 0.719 | 0.533 |
| seg2 V a g | 449 | 33.2% | 33.2% | **33.2%** | 16.0% | 0.747 | 0.512 |
| seg3 V a m | 510 | 46.3% | 46.3% | **46.3%** | 31.6% | 0.760 | 0.548 |
| seg5 V dr | 210 | 39.5% | 39.5% | **39.5%** | 21.0% | 0.713 | 0.526 |
| seg6 V pn | 300 | 53.7% | 53.7% | **53.7%** | 41.3% | 0.710 | 0.570 |

对比 §3 的 conf=0.05 口径（各段球覆盖率 100%）：**抬到 0.40 后覆盖率掉到 25%~54%**。

### 10.2 两个新发现

**① 每帧最佳球的置信度呈双峰分布，[0.10, 0.40) 是空档。**
五段里 `ball_frames_ge_0.10 == ball_frames_ge_0.40` 完全相等（114/114、149/149、
236/236、83/83、161/161）——即"最佳球候选"要么 ≥0.40，要么 <0.10，
**没有任何一帧落在 0.10~0.40 中间区间**。这是 §4"置信度标定崩坏"最直观的证据：
模型对"这是球"要么给出转播域级别的自信（≥0.40），要么给出接近噪声的分数，
中间没有渐变。也解释了 §3 曲线为何在 0.10→0.50 之间是斜坡而非阶跃。

**② conf≥0.40 时每帧恰好 1 个球框，候选洪水自然塌缩。**
实测扫描（seg6/seg3 全段）：所有 ≥0.40 的帧都是"球框数 = 1"，
即 12.83 个/帧的候选在 0.40 处塌缩成 1 个——**输出形态变得和 BallTracer 一样是单球框**。
换言之 0.40 这个阈值刚好卡在双峰的峰谷上，是"能用与不能用"的分界：

| | 每帧球候选 | 球框形态 | 球覆盖率（5 段均值） |
|---|---|---|---|
| conf≥0.05（v0.1） | 12.83 | 洪水，精度 7.6% | 100% |
| **conf≥0.40（v0.2）** | **≈1** | **单框** | **≈39.6%** |
| BallTracer | 1.27 | 单框 | 76.2%（单帧召回） |

### 10.3 目检

- `rf_out40/frames/s6_anno_best.png`：conf=0.71 的红框精准框住粉衣球员脚边的球，
  同帧无任何人类别标签，画面只剩球框 + 轨迹绿点 + 顶部信息条；
- `rf_out40/frames/s2_f50.png`：该帧无 ≥0.40 的球，画面全净（只剩历史轨迹残点）。

### 10.4 这一口径的结论

0.40 阈值让 RF-DETR 的**输出形态**变得可用（单球框、无人类别干扰、画面干净），
但**覆盖率只有 BallTracer 的约一半**（39.6% vs 76.2%）。要补齐覆盖率就得把阈值降回
0.05，那时又回到每帧 12.8 候选、7.6% 精度的不可用状态——**双峰分布意味着没有一个
阈值能同时拿到"干净"和"覆盖"**，必须靠后处理（邻帧补 + 物理门限）把两头的峰拼起来。
这正是 §8 结论"RF-DETR 适合做候选源、不适合做检测器"的量化依据。
