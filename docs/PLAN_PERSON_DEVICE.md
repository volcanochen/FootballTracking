# 方案 B · 设备端实时 · 场上人物检测与稳定 ID 跟踪

> 版本 v0.1（2026-10-18）· 对应需求：**5 秒片段内 ≥85% 帧判对**（帧级口径，见 [`EVAL_PERSON.md`](EVAL_PERSON.md)）。
> 定位：不依赖服务器预计算，**设备端实时**输出人物框 + 稳定 ID。硬件暂未定型，按通用预算设计：**1~2 TOPS int8（或中高端手机 NPU 一档）、输出 ≥30fps、因果约束（不可用未来帧）**。

---

## 1. 结论先行

| 项 | 结论 |
|---|---|
| 可达性 | **帧级 85% 紧张但可达**，前提是三件事同时做到：领域微调、切片等效高分辨率、低分二关联跟踪。缺一不可 |
| 核心矛盾 | 实测证明 **imgsz=640 会系统性漏检 35% 的人**，而 imgsz=1280 端侧算力不允许全帧跑 → 用「切片 + I/P 帧」把等效分辨率抬上去，把平均算力压下来 |
| 复用资产 | 与方案 A **共用同一套微调模型与评测协议**；I/P 帧、门限跟踪、插值参数直接搬 BallTracer |
| 主要风险 | 端侧算力不确定（平台未定）→ 给出三档配置可降级；远景段（s29 类）是最可能不达标的子集 |
| 工期 | 在方案 A 模型基础上 +3~4 个工作日（导出/量化 1d → 端侧推理与跟踪 1.5d → 优化与评测 1d） |

## 2. 实测依据与核心矛盾

（数据同方案 A §2，yolo26n COCO 裸模型实测）

| 配置 | 人数/帧 | 结论 |
|---|---|---|
| 全帧 imgsz=640 | 7.3~8.1 | **系统性漏检 ~35%**（五人场应为 ~11 人） |
| 全帧 imgsz=1280 | 11.1~11.6 | 召回对，但算力是 640 的 4 倍 |
| 2x 上采样 + imgsz=640 | 7.3~8.1 | 无效——YOLO 内部 resize 又缩回去 |

**端侧核心矛盾**：召回要 1280 级分辨率，算力预算只够 640 级。解法不是堆算力，而是**只在需要的区域花分辨率**：

1. 人集中在场地内 → ROI 掩膜砍掉 ~40% 画面（广告牌/看台本来也不该检）；
2. 人相邻帧位置连续 → I/P 帧：只有 I 帧做全画面切片检测，P 帧只对各轨迹预测位置的局部 patch 推理（BallTracer 已验证此机制省 40% 算力）；
3. 漏检是"个体级"而非"整帧级"（实测零检出帧=0）→ 跟踪层低分二关联可以把偶发漏检补住，帧级判对不要求检测器帧帧全对。

## 3. 端侧架构

```
摄像头/视频流 854×356 @30fps
   │
   ├─① 预处理：场地 ROI 掩膜（离线标定一次，每机位一份多边形）
   │
   ├─② 检测（YOLO11n-person 微调，NCNN int8）
   │     I 帧（每 5 帧）：2 切片 × imgsz=640  ← 等效分辨率 ≈ 全帧 1280
   │     P 帧（其余 4 帧）：仅 K 个轨迹预测位置的局部 patch × imgsz=320
   │
   ├─③ ByteTrack-lite（因果版）
   │     恒速预测 → IoU 门限关联（门限随速度自适应，搬球管线 GATE 思想）
   │     低分二关联（≥0.10）→ 恢复个体级漏检
   │     ID 只增不减、断链保留 30 帧（1 秒）——因果约束下不开"未来帧重连"
   │
   ├─④ 帧级兜底：单帧推理超时（>33ms）→ 该帧跳过检测，纯 tracker 预测输出
   │     保证输出恒 30fps，宁可框抖一点也不掉帧（帧级口径下掉帧=直接判错）
   │
   └─⑤ 输出：每帧 [{id, x,y,w,h, conf}]（854×356 归一化坐标）
```

### 3.1 为什么是 2 切片 × 640

| 配置 | 等效像素密度 | 相对算力 | 召回预期 |
|---|---|---|---|
| 全帧 640 | 1× | 1× | 差（漏 35%，实测） |
| 全帧 1280 | 4×（宽向） | 4× | 好，但端侧跑不动 |
| **2 切片 × 640** | **2×（宽向 2 切，高度不变）** | **2×** | 接近 1280（854 宽切成 2 片 427 宽 → 每片 letterbox 到 640 后小人放大约 2.9×） |
| 3 切片 × 640（BallTracer 同款 NX=3, OV=0.20） | 3× | 3× | 更好，算力富余时用 |

注：球管线用 3 切片是球的 3~8px 所迫；人是 35~52px，2 切片起步、实测不够再升 3 切片——**升级路径已预留，切换只改一个常量**。

### 3.2 算力预算（int8，通用 1~2 TOPS 一档）

| 步骤 | 预算 | 说明 |
|---|---|---|
| I 帧：2×640 nano int8 | ~12 ms | nano ~6ms/640@1TOPS 一档（NCNN/MNN ARM NPU 实测量级） |
| P 帧：K patch × 320 | ~2 ms | K=轨迹数(~11)，patch 是共享 batch 一次推理 |
| ByteTrack-lite | <1 ms | 纯 CPU |
| **I/P 混合平均** | **~5 ms/帧** | I:P = 1:4 加权 |
| 预算余量 | 33ms/帧（30fps） | **6 倍余量**，即使平台落在预算下限也有兜底 |

降级三档（平台算力揭晓后直接选）：
- **高档**（≥2 TOPS）：3 切片 + I 帧间隔 5 → 召回最高；
- **中档**（1~2 TOPS）：2 切片 + I 帧间隔 5（默认，本文基准）；
- **低档**（<1 TOPS）：2 切片 + I 帧间隔 8 + P 帧纯跟踪（不跑 patch）。

### 3.3 模型：与方案 A 共用，端侧只做部署

- 同一个 `person11n` 微调权重（方案 A M2 产物），**一次导出 NCNN int8**；
- 量化校准集：full.mp4 均匀抽 300 帧（现成资产），PTQ 预期掉点 <2 mAP（球管线同规模模型经验）；
- 导出后**必须**在 PC 上用 NCNN x86 仿真跑一遍评测协议确认没有量化事故，再上真机；
- 可选增益：person+ball 双类头一次推理（把 BallTracer 的球检测也搬进来）——**v1 不做**，先保证人物达标，避免一次引入两个变量。

### 3.4 因果约束下的跟踪（与方案 A 的本质差异）

| 能力 | 方案 A（离线） | 方案 B（实时） |
|---|---|---|
| 未来帧信息 | 可用（双向修正） | 不可用 |
| 断链重连 | 颜色 ReID + 双向外推 | 只能靠断链保留期内门限自扩（RECAP_STEP 思想，上限 +0.05） |
| 空洞处理 | ≤15 帧插值 | ≤10 帧恒速外推补框，标记 `pred` |
| ID 稳定性手段 | 全局一致化 | 只增不减 + 更保守的 new_track_thresh(0.50) |

帧级 85% 允许每 5s 片段错 22 帧；一次 ID switch 只影响 switch 帧及其后该目标被错配的帧，二关联 + 保守新建门槛能把 switch 频率压到每片段 <1 次。

## 4. 风险与对策

| 风险 | 证据 | 对策 |
|---|---|---|
| 远景段不达标 | s29 conf 中位 0.47@1280、0.35@640 | 评测按机位分层报告（EVAL_PERSON.md）；远景段专属降阈（0.12 冷启动思想）+ 严门限；仍不行则该机位用高档配置 |
| 端侧平台算力不足 | 平台未定 | 三档降级配置（§3.2）；P 帧兜底机制保证不掉帧 |
| 量化掉点 | nano 小模型对 int8 较敏感 | 300 帧本域校准集；掉点 >2 mAP 则改 QAT 或混合精度（首层/末层 fp16） |
| NCNN 切片工程量 | 端侧要自己管 patch 拼接 | 切片逻辑先在 PC Python 侧写好并用评测协议验证，端侧只做等价移植 |
| 遮挡后 ID 换人 | 俯拍人挨人 | 保守新建 + 颜色直方图做**本地**（非全局）关联特征，代价 <1ms |

## 5. 验收与里程碑

验收口径同 [`EVAL_PERSON.md`](EVAL_PERSON.md)，**在端侧部署形态下（含 P 帧/兜底路径）跑**，不是拿 PC 全帧结果交差。

| 里程碑 | 内容 | 工期 |
|---|---|---|
| D1 | NCNN 导出 + int8 量化 + PC 仿真回归（评测协议） | 1d |
| D2 | 切片 + I/P 帧调度 + ByteTrack-lite 跑通，30fps | 1.5d |
| D3 | 三档配置实测帧率/精度曲线，选定平台档位 | 0.5d |
| D4 | 评测达标（FrameAcc ≥ 85%）+ 交付 | 1d |

未达标降级路径：
1. 漏检为主 → 升 3 切片 / I 帧间隔缩到 3 / 远景段专属降阈；
2. ID switch 为主 → 保守新建门槛上调、断链保留 45 帧（牺牲一点新目标响应）；
3. 帧率不足 → 降档位，用 §3.4 兜底路径换帧率。

## 6. 与方案 A 的关系（建议的落地次序）

1. **先做方案 A**：它产出微调模型、标注数据、评测协议三者，是方案 B 的全部上游；
2. 方案 B 是同一模型 + 同一评测的**部署形态**，不是另起炉灶；
3. 两者共用 `tracks` 下发格式，端侧实时方案上线后，服务器预计算仍可作为"高精度校准轨"并存（端侧实时为主、离线修正覆盖远景弱段）。
